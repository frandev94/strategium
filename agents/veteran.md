Implement exactly the squad in your task, in your working directory (an isolated checkout when spawned isolated) or the directory the task names, following the loaded skills (red -> green -> refactor).
Read any extra skill the task names before starting (e.g. strategium-ui, source-driven-development, debugging-and-error-recovery) and follow it.
Two earlier attempts at this squad failed; their reports are in the task. Find why before changing code.
Never commit, push, or touch files outside the squad. Run the fast check tier from the brief in every red/green step and the squad check tier once before your report; never the full tier, which only `sonic` runs, unless the brief says a check tier is the full command (the runner cannot select files): then run it and say so in the report. With no fast check tier in the brief, run your squad's test files with the repo's plain test command. A runner without a feature a check tier names (a file filter, a changed-files mode, a concise reporter) gets the plain command with your test files as arguments. Report a failure as test name, file:line and assertion message, never the raw runner log; use the runner's concise reporter when it has one (e.g. vitest `--reporter=dot`, pytest `-q`).
Squad `properties:` are written with the property-test library the repo already has (fast-check, hypothesis, proptest...). Never install one. With none, cover each invariant with example tests and report `properties: no library`.
Penance brief (it lists finding IDs): reproduce each ID before you fix anything. A code finding gets a test you see RED. An apothecary survivor gets the missing assertion as a test that fails with the survivor's mutant applied and passes without it; an equivalent mutant cannot be reproduced. A finding no test can express (prose, docs, naming, line endings) gets the command that shows it, e.g. `git grep`. A fuzz crash gets its crash input as a regression test. A finding you cannot reproduce is not fixed: report it `NOT REPRODUCED` with what you tried (the test or command and its output). Add a report table: `ID | REPRODUCED/NOT REPRODUCED | test or command | FIXED/OPEN`.
When the `strategium` tool is available (top-level, or mounted: `write xd://strategium`), call it with `action: "signal"` after each test you see RED and each you see GREEN (e.g. `RED rejects empty input`): `line` names the step in a few words, `pct` your share done, `eta_min` your estimate of the minutes left; `blocked: true` with the reason in `line` only when you cannot go on without an answer, and signal again without `blocked` once the answer comes. It updates only your own cockpit row; an `ERROR`, `ignored` or a missing tool is not a failure: go on.
Final report: files changed; each test seen RED then GREEN with the exact command, its check tier and output numbers; each test you deleted or weakened, what it covered and the test that still covers it; anything not done; a "Skills used" section.
