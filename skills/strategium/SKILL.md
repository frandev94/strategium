# Strategium (orchestrator workflow for one objective)

The main session is the **Captain** in the Strategium. It plans, delegates, guards the seals and keeps the theatre's systems in order. The user is the **Chapter Master**: only they grant the purity seals. Station names, agent names, todo items and chat alerts have their own voice. Who belongs to the Chapter and who is an external Imperial organisation is set out in `docs/chapter.md`.

## Objective

A run works one objective. The prompt names it in one of three forms:
- `"free text"`: the objective in the user's words.
- `@path`: a spec or a plan file (an approved omp plan included). A plan that already has Squads (a section still called Slices counts) and a Merge bar is adopted in Scriptorium instead of written again.
- a key: a ticket the theatre knows, or a short name the user chose.

`<KEY>` is the ticket key as given, or else the slug `/strategium` derived: a file's base name, or the free text's first words (ASCII, kebab-case, at most 32 characters, e.g. `add-a-dark-mode`). It names the branch, the `local://` files and the claim.

## Ticketing (optional)

Ticketing is on when the objective is a ticket of the theatre, or when the user gives a booking. It adds:
- the ticket text and its acceptance criteria, verbatim;
- the booking: the minutes booked for the work today, and the booking timer with its 50/80/100 % alerts, stand down and daily shifts (see Timer);
- the theatre's status changes, and the time records.

Without ticketing the run is untimed: its time is still counted (`status`, `report`), but there are no alerts, no stand down and no shifts. The acceptance criteria come from the librarian's spec, and seal Plan is always on (an approved omp plan already is seal Plan), because that is where the user confirms them.

## Theatre

The prompt names a theatre skill (e.g. `skill://strategium-<name>`), or says "no theatre". Read the theatre skill first; if it cannot be read, tell the user and run with no theatre. The theatre supplies the steps marked **[theatre]**:
- **Muster:** the work source, ticket text and acceptance criteria, the booked minutes, status changes, chat language.
- **Repo:** where repos live.
- **Delivery:** commit, MR and pipeline conventions.
- **Records:** where the log goes; how time is booked.
- **House rules:** the rules that override this skill.
- **Extra skills:** skills that briefs must name on top of the core's (per squad kind, study notes).

With no theatre, skip all external writes: the delivery is the branch with its commits, nothing is pushed. With ticketing on and no theatre, ask the user for the booked minutes and the acceptance criteria.

The kickoff may say `no theatre was named`: naming no theatre is not the same as "no theatre" or `none`, which are a choice, and a theatre set in `STRATEGIUM_THEATRE` counts as named. With none named, find the repo in the Objective: an issue URL names `OWNER/REPO`; else the session cwd's git repo; else ask the user for a path, `OWNER/REPO` or no theatre. An issue URL on github.com, or `git -C <repo> remote get-url origin` on github.com with `gh repo view OWNER/REPO` succeeding → read `skill://strategium-github` and call `begin` again on the same key with `theatre: github`. Otherwise run with no theatre; when `gh` is missing or logged out, say so and point to `/skill:strategium-setup`.

## Requirements

- Plugin `agent-skills@addy-agent-skills`, which provides the skills the agents autoload and the briefs name. Install it with `omp plugin marketplace add addyosmani/agent-skills` and then `omp plugin install agent-skills@addy-agent-skills`.
- Install or check everything with `/skill:strategium-setup` (plugin link, dependencies, tools, `.env`).
- Agents pick their model through the omp role aliases `@plan`, `@task` and `@slow` (the bundled `scout` and `sonic` use `@smol`), so each machine's `modelRoles` decides the models; each agent sets its own effort, which a `:level` suffix on its role overrides. The `confessor` is the exception: it names `gpt-6-astra` first on purpose, so the second review comes from another model family when available. See `docs/models.md`.
- Cost tiers: each squad runs its battle-brother on the squad's tier (`light` `@smol:medium`, `standard` `@task:medium`, `heavy` `@slow:high`); the plugin sets that model and effort when it spawns the agent. The user overrides the selectors with env `STRATEGIUM_TIERS` in `~/.omp/agent/.env`: `;`-separated `tier=selector` entries, e.g. `light=anthropic/claude-haiku-5-5:low;heavy=@task:high`; a missing tier keeps its default, and `strategium` `status` prints the `TIERS` line in force. See `docs/models.md`.
- Optional: env `STRATEGIUM_THEATRE` (default theatre for `/strategium`; empty → the GitHub theatre when the run's repo is on GitHub); env `STRATEGIUM_NOTIFY` is off by default (`1` turns on the alarm, the plugin's bundled vox sounds and desktop notifications); env `STRATEGIUM_SOUND` and env `STRATEGIUM_TOAST` are on by default (`0` turns off the alarm's sound or its desktop notification; the user sets them per session with `/strategium-config sound on|off` and `toast on|off`); env `STRATEGIUM_ARCHMAGOS` is off by default (`1` lets a run mark the Archmagos Dominus in Muster; the user sets it per session with `/strategium-config archmagos on|off`); env `STRATEGIUM_COMMIT` is off by default (`1` gives runs the Commit seal; the user sets it per session with `/strategium-config commit on|off`); env `STRATEGIUM_IDLE_MIN` (whole minutes, default 3, `0` off) pauses the run's clock after that many idle minutes. Env `STRATEGIUM_COCKPIT_KEY` (default `alt+c`, e.g. `f8`) sets the key that opens the cockpit; `/strategium-config cockpit-key <key>` saves another for the next omp start. Env `STRATEGIUM_COCKPIT_THEME` (default `blood-angels`; also `ultramarines`, `dark-angels`, `cogitator`) sets the cockpit theme when none is saved; `/strategium-config cockpit-theme <name>|default` saves it and applies it at once. Env `STRATEGIUM_RELIC` (`1` on, `0` off, off by default) gives the cockpit a worn relic look (worn frame, truecolor tarnish, scratches; wide layout only) when no choice is saved; `/strategium-config relic on|off|default` saves or drops the choice and applies it at once.
- Optional cockpit caster, off by default: env `STRATEGIUM_CASTER` (`1` on, `0` off, used only when no choice is saved; `/strategium-config caster on|off|default` saves or drops the choice and applies it at once) makes a fast model write a short summary of the current station in a `CASTER` box of the cockpit while it is open, at most once per interval and only when the station state changed. Env `STRATEGIUM_CASTER_EVERY_MIN` (whole minutes, default 1) sets the interval; env `STRATEGIUM_CASTER_MODEL` (default `@smol`) is an omp role alias and must start with `@`. It reads only the cockpit's status lines and chronicle, never transcripts, and never writes to or asks an agent. Its cost is the `caster` row of the run report.
- Optional agent names, off by default: env `STRATEGIUM_NAMES` (`1` on, `0` off, used only when no choice is saved; `/strategium-config names on|off|default` saves or drops the choice) makes the plugin hand out each agent's name through `strategium` action `name` (lore names such as `BrotherLorenzo`, no duplicate inside a run, kept across an omp restart) and refuse a spawn whose name it did not hand out. It is off by default because that guard refuses every unnamed item; `strategium` `status` shows `NAMES on|off (<source>)`. With names off nothing is refused and `name` answers with an error. Turn names on before a run begins: a squad already spawned keeps the state it started with, and another omp window reads the setting only when it starts. With names on, a shared roster (`roster.json` in the state dir, written under a lock) keeps each builder surname's service record and hands a new squad the best available brother, skipping the corrupted and those on another run's campaign; for the Laurel Imperialis to count, the Captain merges with `gh pr merge` (or `glab mr merge`) from its own bash, and `end` may print `ROSTER <n> squad(s) recorded` or `WARN ROSTER not written: …`. See `docs/chapter.md`.

## Todo and agents

Build the run's todo with `todo.ts` (skeleton below; in omp plan mode add `--to Scriptorium`) and start the Objective task. Build every todo with `todo.ts` from this skill's directory: it tags each task with its agent, checks the agent names and the duplicates the todo tool would refuse, and owns the glyph table. Write the stations as unindented lines and their tasks indented below (`agent: text` or `[agent] text`), then pass each printed JSON line to `todo` as it is:

```bash
bun "$(realpath skill://strategium)/todo.ts" <<'EOF'
Muster
  captain: Objective
  captain: Orders
Auspex
  scout: Map the code the objective touches
Scriptorium
  librarian: Plan as squads → local://<KEY>-plan.md
Deployment
  captain: Branch and squads
Skirmish
  battle-brother: Build the squads
Inquisition
  inquisitor: Review the diff against the Merge bar
  sonic: Run the checks
Extraction
  captain: Delivery
Debrief
  captain: End the run and records
EOF
```

`todo.ts` uses glyph tags (`<glyph> librarian · Plan…` instead of `[librarian] Plan…`) when `STRATEGIUM_GLYPHS=1`, the same switch as the footer. `--append` prints one `append` call per station instead of one `init`: Orders uses it for the chosen seals and the archmagos task, and squads, penances and returns use it for their items. `--from <station>` keeps that station and every later one, `--to <station>` keeps every station up to and including it; both work with `init` and `--append`, the station names come from the list you give it, and an unknown one is an error.

## Timer (servo-skull, ticketing only)

The servo-skull is the booking timer: a monitoring device, not an agent (`sonic` is the servitor).

Every run begins untimed: `/strategium` begins it, or Objective does when the skill runs without the command. A run is timed once `begin` or `start` gives it `booked`, which Orders does with the booking; only a timed run has a booking. An untimed run shows `● 🪐 strategium: <KEY> · <station> · <elapsed> min` in the footer and none of the alerts, stand down or shifts below.

Tool `strategium`: `begin | repo | start | stop | add | status | report | end | attention | slices | notify | redraft | reuse | name | rate | signal (subagents only) | seal`. `seal (lines)` fills the cockpit's seal panel for the seal that waits. User commands: `/strategium <objective>` starts a run; `/strategium-pause`, `/strategium-resume`, `/strategium-add`, `/strategium-status`, `/strategium-config`, `/strategium-cockpit`, `/strategium-end`. The footer shows `● 🪐 strategium: <KEY> · <station> · <stage> <elapsed>/<booked> min (<pct>%)`: the dot is green under 80 %, yellow from 80 %, red from 100 %, grey `○ … paused` while paused; the stage icon follows the booking: blue world under 50 %, amber meteor from 50 %, orange fire from 80 %, red nuke from 100 %. The station comes from the todo: `↩ <station>` when the run returned there, and `⏳ seal <name>` in yellow when a seal waits for the user. With `STRATEGIUM_GLYPHS=1` the icons are Nerd Font glyphs. Elapsed includes the `spent` minutes given to `begin`, and `report` lists them apart as `PRIOR` (an estimate, not a measured block).

Cockpit: `/strategium-cockpit` (also Alt+C or the configured cockpit key) opens the user's overlay: the key, clock and the seals as a chain (`✠ Plan → ○ Demo`; no SEALS row when the run has no seals), then the active station as the title by default (the user browses the others with ←/→ and Home returns; the title then reads `viewing · active: <name>`; ↑/↓ move a `▸` cursor over lines and chronicle entries, Tab jumps box, Enter opens the detail of the selected line (squad, agent, seal, chronicle entry or task; ↑/↓ scroll it; Enter again in an agent detail, or in a squad detail with agents, opens that agent's read-only transcript, newest row first, following new entries: `TRANSCRIPT <id>`, rows `user:`, assistant text, `→ tool intent`, `← tool ok|error: …`, the final answer when done, a one-line reason when there is no transcript; it is the one keypress that reads a file), Backspace goes back to the lines with the cursor kept, Esc goes back one level inside a detail and closes at the top level, `q` closes from any level in one press), with one box per agent tag present in it (CAPTAIN, SCOUTS, LIBRARIANS, BATTLE-BROTHERS, APOTHECARIES, INQUISITOR, SECURITY-REVIEWER, SONIC, ADEPTS), one marked line per task, squad or agent, and the chronicle. The waiting seal shows in the station title and the footer, and a full-width seal panel shows what the Captain prepared while it waits. The Captain drives only the seal panel, through `seal`. It reads the todo, so agent tags and `[seal] <name>` items must stay exact. It cannot show test or mutant counts from inside subagents. Under each running agent or squad it draws a status row from the agent's own file: elapsed time, then its cost (`$0.42`, or `$?` while no usage is known), then `done/total · ~ETA · current task` from its todo, else its last intent; a subagent's own `signal` (`pct`, `eta_min`, `line`) replaces `done/total`, the ETA and the task text, and `blocked: true` draws gold, logs once and rings the `attention` alarm once per block (the Captain learns of it from the user or from the chronicle entry `blocked: <line>` in the cockpit, reads the agent's progress at `agent://<id>` and answers it by IRC or a new brief; never call `signal` yourself); a blocked row with nothing in flight for 5 min is also marked stalled; gold `stalled Nm` (logged once) once it has made a tool call, after 5 min with none in flight and none ended (an agent with no live row yet shows elapsed only); elapsed only when the agent has no host id.

Footer contract: the station part is `<station> › <task>`, where `<task>` is the active todo task's text without its agent tag, cut to 32 characters with `…`. A seal keeps `⏳ seal <name>` with the whole name (`Demo (2)`); a return shows `↩ <station> › <task>`. The footer appears as soon as `/strategium` begins the run (`strategium: <KEY> · <elapsed> min`). Once the skeleton's first task is started it shows e.g. `Muster › Objective`, then `Muster › Orders` (an `ask` signals on its own; Orders has no `⏳`). A `todo init` that rebuilds a run's todo does not move the footer (omp starts its first task by itself); the next `start` or `done` does. The exception is the hand-off after an omp plan approval: an `init` whose stations share no name with the current ones (Deployment onwards replacing the plan-mode stations) moves the footer to its auto-started first task (`Deployment › <task>`). On a wide enough terminal the line ends, flush right, with the dim hint that names the cockpit key (`ALT + C to enter cockpit` by default; no hint when it does not fit or the width is unknown).

Parallel runs (timed or not): each omp session owns one run (its objective, edit guard, footer and alerts), held through an atomic claim on its `<KEY>`. To work two objectives at once, run each in its own omp session; both count their time at the same time. A `begin` for a key another session holds fails and names that session's id. Closing a session pauses its run and releases the claim; reopening that session takes it back and resumes it on its own, unless the user had paused it (`/strategium-pause`, action `stop`, the stand down). A timed run on a new day stays paused until today's booking is given. While the claim is released, another session's `begin` can take it. Only when the user says the holder crashed, pass that id as `takeover` (begin or end); it replaces the holder only if it is still that one. A session whose run was taken over drops it and stops acting on it. `status` lists every run; `report` adds an `OVERLAP` line with the minutes two runs ran at once, which the user splits before booking time.

Idle pause: the plugin pauses the run's clock after `STRATEGIUM_IDLE_MIN` idle minutes (default 3, `0` off; the user sets it per session with `/strategium-config idle <min>`), plays the `idle` sound (with notifications on) and shows the footer paused. The next turn resumes the clock on its own: after an idle pause do not call `start`. A run the user paused by hand (`/strategium-pause`, action `stop`, the stand down) never resumes by itself; only `/strategium-resume` or `start` does. A timed run on a new day still needs today's booking. A question (`ask`) or plan review waiting for the user counts as busy: the clock keeps running and the `attention` alarm sounds (with notifications on).

Shifts (timed runs only): a booking is per day, so each day is its own shift. A ticket that spans several days keeps its run (ticket, repo, claim); every day it counts from 0 against that day's booking. On a new day `/strategium-resume` (or `start` without `booked`) cannot reuse yesterday's booking: the plugin asks the Captain to fetch today's (theatre Muster; not booked today → tell the user and stop), then call `start` with `booked`. A session reopened on a new day does not resume by itself: its run stays paused until today's booking is given. `/strategium-resume <min>` or `start` with `booked` sets it directly. An untimed run resumes on a new day without asking. A run still counting at midnight keeps counting: the plugin ends its block at 00:00 in yesterday's file and starts one at 00:00 today; a timed run then counts without a booking and without alerts (footer `<elapsed> min · new day: /strategium-resume <min>`) until today's booking is given, so fetch it as above.
Manual time: `/strategium-add <min>` (tool action `add`, `minutes`) adds minutes to today's time for the ticket, or removes them with a negative number (e.g. work done away from the keyboard, a forgotten pause). Only for minutes the user names. They count toward the alerts; `report` shows them as `ADJUST` and in each ticket's `worked` total.

Every minute the plugin checks the booking. At 50 %, 80 % and 100 % it plays a sound and posts `TIMER <p>% <KEY> <elapsed>/<booked> min` into the session. It reports the highest threshold crossed since the last alert, so a run that starts past one skips it. On that message:
- **50 %:** tell the user.
- **80 %:** tell the user and compare with the pending todo items. If the rest will not fit, say so now, with the reason.
- **100 % (stand down):**
  - start no new agents;
  - send running agents (`write agent://<id>`) "Wrap up: stop at a safe point, do not commit, report state";
  - call `strategium` `stop`;
  - report what is done and what is left;
  - continue only on the user's explicit order.
- A standing order recorded in `local://<KEY>-muster.md` ("continue past the booking") replaces the stand-down steps for that run: on TIMER 100 % tell the user in one line, record the order with the reason, and keep going; no wrap-up messages, no `stop`. The user withdraws it at any time.

## Resume (objective already in progress)

When the work has commits or uncommitted work from an earlier session, run the stations with these changes:
- Muster: in **Objective**, record the starting state (`git log origin/main..HEAD --oneline`, `git status --short | wc -l`) in `local://<KEY>-auspex.md`.
- Auspex: scouts map what is done and what is left, not the whole codebase. Large transcripts are read by tail range only (e.g. `:-300`), and a scout writes its partial result before reading more.
- Scriptorium: the librarian plans only the remaining work; squad 1 finishes and verifies the in-flight work so the tree is green first.
- Deployment: no new branch over a dirty tree; on a dirty tree, squads run non-isolated in place, one at a time.
- Inquisition: commits that are already clean Conventional Commits stay; no `git reset --soft origin/main`. New work goes in as new commits on top.
- Orders: the seals as the user chooses (e.g. Demo per card); Commit follows the commit setting.

## Returns

Hard rules: `rule://strategium-stations` (Returns).

A run goes back instead of forward.

| Return | Trigger | Target | Budget |
|---|---|---|---|
| **Recon** | the map of the code is wrong: a file the scouts missed, a helper that is not there | one more `scout` with that exact gap | 1 per run |
| **Redraft** | the plan is wrong: scope beyond the ticket, squads that do not cover the acceptance criteria, or a squad whose acceptance check cannot be satisfied as written, or the user rejects the plan at seal Plan | the Captain calls `strategium` `redraft` (both paths; it records the run's one redraft). Back to Auspex, targeted: 1-2 `scout`s get only the trigger, the output of `git log --oneline origin/main..HEAD` and `git diff --stat origin/main..HEAD` (the Captain runs them), and the files of the remaining squads; the Captain writes their findings as `## Redraft` in `local://<KEY>-auspex.md` (what changed since the first map, what it got wrong). Then Scriptorium: the same `librarian` or a new one re-plans the remaining work from the refreshed map; with areas, only the affected area is redrafted (its librarian, or a new one given its part file and the gap) and the lead integrates again; with the archmagos, one new `archmagos` gets the current plan, the redrafted part, `## Redraft` and the gap. The plugin refuses any librarian or archmagos spawned after `redraft` until a scout spawned after it has finished. What already passed stays as it is | 1 per run |
| **Penance** | the code is wrong: acceptance check red, apothecary survivors, fuzz crashes or a `flaky (new)` failure, BLOCKING findings | a `battle-brother` fix run with every open finding ID in one brief; it first reproduces each finding, and one it cannot reproduce comes back NOT REPRODUCED; a round after the first asks `strategium` `reuse <squad>` first and may seed a proven builder (see Skirmish) | 2 rounds per squad, one tier up from the squad's tier (heavy stays heavy), then one `veteran` run (heavy); reviewers keep their own tiers |
| **Retrial** | the fixed code needs a new look | the `inquisitor` again (the `confessor` re-checks its own IDs) on the open finding IDs and the fix range only, then `sonic` for the full check tier | 2 rounds per Merge bar item, then the item stays FAIL |
| **Stand down** | the budget is spent, or the failure is not in the code: the ticket is wrong, the environment is broken, a theatre is missing | the user, with the open items and what was tried | — |

- **Seals after a return:** a seal asked again is numbered `[seal] Demo (2)`; after a redraft, `[seal] Plan (2)`. A penance or redraft that changes a contract beyond the sealed Contract section (or adds one to a plan that had none) after seal Plan was granted breaks seal Plan too: a redraft already ends in `[seal] Plan (2)`; after a penance, `todo append` `[seal] Plan (2)` (or the next number) to the station the penance runs in, and show the Contract as sealed and as changed before the run goes on. The user may waive it when the change does not touch what was sealed; record the waiver in the muster file. The Review & merge loop has its own 2-round budget and no `veteran` run (see Extraction); the Contract rule applies there too.
- **NOT REPRODUCED:** a penance whose findings all come back NOT REPRODUCED does not count against the 2-round budget.
- **Flaky (new):** for a `flaky (new)` finding, reproduced means it fails at least once in up to 5 reruns; one passing run does not drop it, and only 5 passing reruns come back NOT REPRODUCED.
- A squad rewritten by a redraft is a new squad with its own penance budget.

## Stations

### 0. Muster [captain]
Hard rules: `rule://strategium-stations` (Muster).
Muster is the skeleton's first station. Two tasks; mark each done when its "Done when" holds, and start the next.
1. **captain: Objective**: read `<KEY>` from `strategium` `status` (`RUN <KEY> … (this session)`). With no run for this session (the skill was started without the command, or the claim was refused and the user decided), call `begin` with `key` (see Objective) and `theatre`, without `booked`. With no theatre named, pick it as Theatre says, before reading the ticket. For a ticket, **[theatre]**: ticket text, acceptance criteria, booked minutes; a ticket that is not booked today → `strategium` `end` and stop. For a file, read it; for free text, take it as written.
   Probe the skills with `read skill://<name>:1-4` (the frontmatter is enough): `spec-driven-development`, `planning-and-task-breakdown`, `test-driven-development`, `incremental-implementation`, `code-review-and-quality`, `code-simplification`, `debugging-and-error-recovery`, `source-driven-development`, `frontend-ui-engineering` and `doubt-driven-development`. If any read fails: `strategium` `stop` (the run stays, paused), tell the user to install `agent-skills@addy-agent-skills` (see Requirements), and stop with the task open. Agents silently skip unknown autoload skills, so this check is the only guard.
   Then probe every skill the theatre lists under **Extra skills** the same way. A missing one blocks the kind of work it covers (all squads, UI squads, study notes): see `rule://strategium-stations` (Muster).
   Gather the booking figures for the ask: with ticketing, the booked minutes (from the theatre, editable) and the minutes already worked today that the timer has not tracked (`strategium` `status` shows what it already has; **[theatre]** proposes a figure from its records, with no theatre propose 0); without ticketing, nothing.
   Run `strategium` `report` and keep its `PROPOSE` lines (a heavier default tier for a squad kind whose builders keep being rated `corrupted`); with none, nothing to offer.
   Read the run's rules (see Rules).
   Done when `<KEY>`, the objective text and its acceptance criteria (if the objective has them) are recorded, the rules are read, every required skill and theatre Extra skill has been probed, and the booking figures are ready. A ticket not booked today ends the run; a failed required probe stops it; either way the task stays open.
2. **captain: Orders**: the defaults are Plan; Demo when the objective has something to see running (a screen, an HTTP API, a DLL loaded by a host); MR when the theatre delivers one. **Ask only when there is a choice.** The Orders `ask` opens only when it has a real field:
   - the booking, with ticketing: the booked minutes and the untracked minutes from Objective, editable;
   - Demo to toggle (the objective has something to see running) or MR to toggle (the theatre delivers one), checked by default;
   - "After the PR: independent review until clean, then merge", unchecked by default (only when the theatre delivers a PR), recorded in the muster file as the seal `Review & merge`;
   - Plan, checked, only inside an ask that opens for another field; it can be unchecked only with ticketing (an approved omp plan leaves it out);
   - the fields a theatre adds (see the theatre skill);
   - the Archmagos box: when the `ARCHMAGOS` line of `strategium` `status` reads `ARCHMAGOS on`, the checkbox "Archmagos Dominus para el plan", unchecked by default; with the setting off, no checkbox.
   - each `PROPOSE` line that `report` gave at Objective, as one field: `<kind> squads: default tier <next> instead of <t>`, unchecked by default. The muster file records the answer; an accepted one goes into the librarian's brief as `Default tier for <kind> squads: <tier> (the user's choice at Muster)`. The plugin stores no per-kind default, so the proposal comes back in later runs while the counts hold;

   With no such field there is no `ask`: the Captain takes the defaults. Without ticketing Plan cannot be unchecked (an approved omp plan already is seal Plan). The optional booking of a run without ticketing is no reason to open the ask; it shows only inside an ask that opens anyway, and left empty the run stays untimed. The user can time it later by asking the Captain, who calls `start` with `booked`. Commit follows the commit setting. When the `COMMIT` line of `strategium` `status` reads `COMMIT on`, the run has the Commit seal (the muster file records it with that source); with the setting off, Commit is off unless the user asks for it in words (`rule://strategium-stations`, Muster). An objective that is an approved omp plan leaves Plan out of the ask. In omp plan mode Orders runs as here, in the plan-mode session, before Auspex: one `ask` when it has a field, with no Plan box (omp's plan approval is `[seal] Plan`). Booking and the Archmagos box go through the same `begin` calls, so both are recorded in the plan-mode session. `[seal] Plan` is appended to Scriptorium as usual, and the Captain starts it when proposing.
   When the user's answer changed `booked`/`spent`/`archmagos`, call `begin` again on the same key with `booked`/`spent` and the run's `theatre`, plus `archmagos: true` when the box was checked. Either way: **[theatre]** make the status change for the ticket (in omp plan mode, at Deployment of the fresh session; see Scriptorium); if elapsed is already ≥ the booking, apply the 100 % rule now, before any agent starts: say so with the reason and continue only on the user's explicit order. Write `local://<KEY>-muster.md` (with or without an ask): the KEY, the objective verbatim, its acceptance criteria (if any), the seals, the booking (or that the run is untimed), the theatre, the standing orders and an empty `## User tasks` section. Append with `todo.ts --append`, which adds at the end of a phase, so in this order: with the Archmagos box checked, first the Scriptorium integration task `archmagos: Integrate the plan → local://<KEY>-plan.md`; then the run's seals: `[seal] Plan` to Scriptorium, `[seal] Commit` to Skirmish (when the commit setting reads on), `[seal] Demo` to Inquisition, `[seal] MR` to Extraction (after `captain: Delivery`, whose push waits for it), then, when that box was checked, `captain: Review & merge loop` to Extraction after `[seal] MR` (not a `[seal]` item: the plugin treats those as waiting for the user; the seal stays recorded in the muster file only); that item is done when the loop ends, merged or stood down.
   In omp plan mode append with `todo.ts --append --to Scriptorium`: only the archmagos task and `[seal] Plan` enter the todo. The later seals (Commit, Demo, MR, the Review & merge loop) are recorded in the muster file only and enter at the rebuild after approval.
   Done when the user answered, or no ask was needed, `begin` has succeeded (the second call only when it was needed, and the theatre's status change is made, if it has one; in omp plan mode it waits for Deployment), the muster file is written and the last `todo append` has succeeded. Then `todo start` the first Auspex task (in omp plan mode too: Orders is done before Auspex).

### 1. Auspex [scout]
Hard rules: `rule://strategium-stations` (Auspex).
- **[theatre]** Find the repo. Then call `strategium` `repo` with its absolute path; this arms the edit guard.
- 1–3 `scout` agents in one `task` batch, distinct focuses: code paths the ticket touches; existing helpers, patterns and tests to reuse; repo conventions (MR template, commit rules, i18n, test and check commands as the three check tiers of `## Checks` (below; the Captain gives this scout the three tier definitions from that bullet), the property-test library if any, repo skills, line endings (`.gitattributes`, `git config core.autocrlf`, `git ls-files --eol` grouped by extension)). Briefs give file ranges for anything large (transcripts, logs, generated files).
- The Captain writes `## Checks` in the auspex file from the conventions scout: three check tiers, each with its exact command. **fast**: the narrowest command that runs the one test being written (one test file or one test name; a changed-files mode such as `vitest related` or `jest -o` only when the repo's runner has it), seconds, for every red/green step. **squad**: a squad's own test files plus the cheap static checks on its files (typecheck, lint), for its acceptance check before the report. **full**: every check command the repo's CI runs; only `sonic` runs it, besides the apothecary's survivor confirmation. Every command follows `rule://strategium-stations` (Auspex). A runner without a feature a tier would use (a file filter, a changed-files mode, a concise reporter) gets the plain command: the fast and squad tiers pass test files as arguments, and with no way to select files they are the full command: the `## Checks` entry then says so, and builders may run it (their brief tells them).
- One `sonic`, started after the scouts have finished and given the draft `## Checks` in its brief (it confirms or corrects the fast and squad commands by running them once), runs the full check tier once on `origin/main`, alone (no other check, build or `sonic` running), and reports exact numbers, each command's wall time, the slowest test files when the runner reports per-file times, and every failing test by name. It reruns each failing test once: one that passes on the rerun is `flaky`. It also runs the fast and squad tier commands once on one existing test file and says whether each works; one that does not falls back to the next check tier up, and the Captain writes that fallback in `## Checks`. The Captain records the numbers, the times and each failure (`known` or `flaky`) under `## Baseline` in the auspex file. Briefs pass those failures with their label (known or flaky), and the Merge bar compares against them. In omp plan mode subagents have no bash, so the Captain writes `## Baseline: pending (plan mode)` instead, and the fresh session runs this `sonic` first in Deployment.
- The Captain merges their outputs into `local://<KEY>-auspex.md`.
- Split: when the plan will need 2 or more areas that barely share files, or more than about 5 squads, the Captain divides the objective into areas from the scouts' map and writes `## Areas` in the auspex file: one row per area (kebab-case name, files, the acceptance criteria it covers). Every criterion belongs to exactly one area. Below that, one librarian, as now. A run marked for the archmagos always writes `## Areas` with at least 2 areas, because the plugin refuses the archmagos before 2 librarians have finished.
- If later work shows the map is wrong, correct it with one recon (see Returns).

### 2. Scriptorium [librarian] → seal Plan
Hard rules: `rule://strategium-stations` (Scriptorium).
- One `librarian` agent with the objective (a ticket's text with its acceptance criteria verbatim, the file, or the free text) and `local://<KEY>-auspex.md`; it writes `local://<KEY>-plan.md` (Spec, Contract when the plan changes one, Squads, Merge bar). Without ticketing, the Spec proposes the acceptance criteria. An adopted plan that already has Squads and a Merge bar is checked against the auspex map and written in that shape, not planned again.
- Several librarians (the auspex file has `## Areas`): one `librarian` per area, all in one `task` batch, each item's `name` set to its area. The task result returns each librarian's id (omp adds a numeric suffix when a name is taken); the Captain hands those ids on, and the others reach a librarian only with `write agent://<id>`. Each brief has the objective, `local://<KEY>-auspex.md`, its area row, its output file `local://<KEY>-plan-<area>.md` and the other areas' names. Each writes its part there: Spec for its criteria; Contract (only when its squads change one); Squads with id (prefixed `<area>-`), parallel, files and check; `Needs from other areas`; no Merge bar. A librarian that needs something from another area (an interface, a shared file) writes to that area's librarian with `write agent://<id>` instead of assuming it. After the split the Captain appends one `librarian: Plan <area> → local://<KEY>-plan-<area>.md` task per area with `todo.ts --append` and `todo start`s the first area task; the "Plan as squads" task becomes the lead's integration and starts after them.
- With `NAMES on`, each librarian item's `name` comes from `strategium name` with `agent: librarian` (a new name per call), and the area goes in its brief. With names off the `name` is the area, as above.
- Integration: after the batch, a lead librarian merges the parts into `local://<KEY>-plan.md` (Spec, one Contract when any part has one, Squads, one Merge bar): the first of the batch (idle, with its context), given all the parts with `write agent://<id>`, or a new librarian given every `local://<KEY>-plan-*.md`. It resolves each `Needs from other areas` entry, gives every shared file one owning squad or puts the squads that share it in sequence (`parallel: false`), and writes one Merge bar. There is still a single `[seal] Plan`.
- Archmagos (the run was marked in Muster): after the area batch, one `archmagos` replaces the lead librarian. Its brief has the objective, `local://<KEY>-auspex.md` and every `local://<KEY>-plan-*.md`. Its final answer is saved byte-for-byte with `cat agent://<id> > local://<KEY>-plan.md`, in every mode. Gap fixes before seal Plan go to the same archmagos with `write agent://<id>` (a follow-up is not a new spawn) and are saved the same way. At seal Plan the Captain shows Squads, Contract (when the plan has one), Merge bar, Pre-mortem and Open for seal Plan. The plugin refuses the archmagos when the setting is off, the run is not marked, fewer than 2 librarians have finished, it is a second one without `redraft`, or a redraft still waits for its refresh scout; on a refusal the lead librarian merges as before.
- Challenge gaps: scope beyond the objective, squads without a check. Fixes go back to the same librarian (`write agent://<id>`).
- Tiers: every squad of the plan has `tier: light|standard|heavy — <reason>`. At seal Plan the Captain shows a table `squad | tier | reason | estimate` (estimate = the squad's cost and time from the table below), the run total, and the `TIERS` line from `strategium` `status`. The estimate is rough on purpose and fixed:

  | Tier | Relative cost (light = 1) | Time per squad |
  |---|---|---|
  | light | 1 | ~5 min |
  | standard | 3 | ~10 min |
  | heavy | 10 | ~20 min |

  Run estimate: the cost is the sum over the squads; the time is the slowest parallel squad plus each sequential squad.
- Changing a tier is not a redraft. At seal Plan the user approves or answers with changes such as `S2 heavy`: the Captain edits that squad's `tier:` line in `local://<KEY>-plan.md`, computes the estimate again and shows it again; no redraft budget is spent. Until the squad's first battle-brother spawns (omp plan mode included) a tier change is made the same way, and the Captain then calls `slices` again with the new tier. In omp plan mode the tier table goes in the body of the `xd://propose` plan, and a "Refine plan" that only changes tiers is not a redraft: the Captain edits the tier lines, declares the slices again and proposes again.
- In omp plan mode subagents can only read and search (no write, no spawns, no messages). The Captain launches the scouts as usual. The librarian's brief asks for the whole plan (Spec; Contract when the plan changes one; Squads with id, parallel, files, tier, acceptance check; Merge bar) as its final answer. The Captain saves it byte-for-byte with `cat agent://<id> > local://<KEY>-plan.md` (`rule://strategium-plan-copy`). Gap fixes go to a new librarian run given `local://<KEY>-plan.md` and the gaps (with the archmagos: `write agent://<id>` to the same archmagos), saved the same way. The Captain proposes the plan with `xd://propose` (body `<KEY>`); omp's plan approval is `[seal] Plan`, with no separate `ask`. The plan body opens with the line `Done in plan mode: Muster, Auspex, Scriptorium.` and then lists only what the approval starts: Deployment (status change, baseline, branch, squads with the tier table), Skirmish, Inquisition (Merge bar), Extraction and Debrief. Before each `xd://propose` (gap fixes included), the Captain declares the squads with `strategium` `slices` and records the `SQUADS` line in the muster file; on a refusal (the tool is unavailable in plan mode, or returns `ERROR`) it records that and declares them at Deployment as usual, and a shared-file `ERROR` is a plan defect that goes back to the librarian as a gap. It then `todo start`s `[seal] Plan` and proposes. After "Approve and execute" omp opens a fresh session; the run (booking, Archmagos mark, squads) and its `local://` files go with it. The Captain rebuilds the todo with one `todo.ts --from Deployment` init: the skeleton plus the later seals and `## User tasks` items the muster file recorded, and `sonic: Run the baseline checks` as Deployment's first task when the baseline is pending. It sends no `todo` `done` for the plan stations: omp starts Deployment's first task itself, and that is where the run is. Deployment does the theatre's status change first, then the pending baseline `sonic`, then the branch and squads; no seal is asked again. With "Approve and keep context" or "Approve and compact context" the run stays in its session: add the remaining stations with `todo.ts --append --from Deployment` (plus those later seals and user tasks), then `todo` `done` `[seal] Plan` (omp starts Deployment's first task) and do the same Deployment steps. A plan-mode rebuild after a compaction uses `--to Scriptorium` again; a re-init after approval, in the fresh session, uses `--from Deployment`, never the full skeleton, which would bring the plan stations back.
- Plan mode with areas: each area librarian returns its part as its final answer, with its `Needs from other areas` listed instead of messages. The Captain saves each with `cat agent://<id> > local://<KEY>-plan-<area>.md` and gives all the parts to a new lead librarian, whose answer is saved with `cat agent://<id> > local://<KEY>-plan.md` and proposed as above (with the run marked, the archmagos is that lead; one `[seal] Plan` through `xd://propose`); the squads are declared from the lead's plan before proposing, as above. On a redraft only the affected area's librarian is re-run, then the lead.
- In omp plan mode, "Refine plan" in the review is a rejection at seal Plan: the Captain drops `[seal] Plan` and calls `redraft`; if `redraft` is refused in plan mode, it records that in the muster file and calls it at Deployment (then the refresh guard does not apply, and an archmagos refusal falls back to the lead librarian, as above), and a second rejection still stands down. The scouts return their findings as final answers and the Captain writes `## Redraft`; a new librarian (with the archmagos, one new `archmagos`) re-plans, and the Captain declares the squads again, starts `[seal] Plan (2)` and proposes again.
- `[seal] Plan`: show the squads, the Contract section when the plan has one (HTTP endpoints and their shapes, a migration, a persisted schema, DLL exports and their ABI: each item as it is on `main` and as the plan changes it), and the Merge bar. A later change to that Contract breaks seal Plan (see Returns).
- The plan can be redrafted once (see Returns). Re-plan from `## Redraft` in the auspex file; a `write agent://<id>` to the same librarian goes only after the refresh scout has finished, and the re-plan ends in `[seal] Plan (2)`. With areas, only the affected area is redrafted, by its librarian or a new one given its part file and the gap, and the lead then integrates again (with the archmagos: the area's librarian redrafts its part and one new `archmagos` re-integrates only that area; budget stays 1 per run). A seal Plan the user does not approve is a redraft: `todo drop` the rejected `[seal] Plan`, call `redraft`, and follow the same path; a second rejection finds the budget spent and stands down. The Merge bar items that were already PASS stay PASS.

### 3. Deployment [captain]
- After an omp plan approval: the theatre's status change, then the pending baseline `sonic`, then the branch.
- Branch `<type>/<KEY>-<short-name>` from `origin/main` in the main checkout; for a slug key, `<type>/<KEY>`.
- Declare the plan's squads (skip when the muster file records them declared before an omp plan proposal): `strategium` `slices` with each squad's `id`, `parallel`, `files` and `tier` as the plan lists them (an omitted tier is `standard`). The plugin refuses parallel squads that share a file while both may run: redraft the plan instead of editing the declaration. A squad whose agents have all stopped no longer counts; listing it again gives a `WARN` line (remove it from the list), and a new squad changing its files gets a `WARN` to brief that agent with what the stopped squad changed.
- No drop pods: omp gives every isolated agent its own checkout and lands its work on the run's branch (`task.isolation.enabled: true`, `task.isolation.merge: branch`).

### 4. Skirmish [battle-brother] [apothecary]
Hard rules: `rule://strategium-stations` (Skirmish).
- Parallel squads: one `task` call with one `battle-brother` item per parallel squad, every item `isolated: true`, so the plugin knows which squad each agent builds. With names off the item `name` is the squad id. With `NAMES on` (`strategium` `status`) every `task` item's `name` comes from `strategium name` instead: `agent` plus, for `battle-brother` and `veteran`, the `squad` id. `slices` prints the parallel squads' first Brothers on its `NAMES` line, and a squad's Brother name stays the same until it has spawned. The brief still says `build squad <id>`. The plugin refuses a builder (a penance or veteran included) on files another running builder is changing: wait for that agent first. Sequential squads: one isolated battle-brother at a time, after the parallel ones landed. Penance and veteran runs are isolated too.
- The plugin sets each builder's model and effort from its squad's tier when it spawns. With names off, a penance is named after the squad whose findings it fixes, so the item `name` must be the squad id. With `NAMES on` it asks `name` for that squad and gets the Penitent (after the squad's Brother has spawned), the veteran gets the Veteran, and the plugin finds the squad through the recorded name. The squad is the one whose findings the penance fixes (the one with the highest tier when it spans squads); the plugin runs it one tier up from the squad's tier, heavy staying heavy. A parallel batch may mix tiers.
- With `NAMES on` a spawn the plugin refuses keeps its name: ask `name` again for the same squad and use the same name. A name that has spawned is never reused. A retrial of a non-builder agent asks with `again: true` (the same persona, a new epithet), and a redraft makes the old builder names obsolete, so the re-planned squads get new ones. Titles and lore are in `docs/chapter.md`. With `NAMES on`, every `task` item and every `agent(label=…)` eval spawn asks `strategium` `name` first, scouts, `sonic`, reviewers and the generic `task` agent included. After a refused spawn omp may show the retried id as `<Name>-2` (omp's suffix); the plugin maps it back to the name.
- Each brief: `Read local://<KEY>-plan.md; build squad <id>` plus what the plan cannot know: the fast and squad check tiers from `## Checks` (the full check tier stays with `sonic`; if `## Checks` is missing because the plan-mode baseline is pending, builders run their squad's test files with the repo's plain test command), the baseline's known and flaky failures, the auspex conventions, and the interfaces of squads already landed. Quote the user's strings verbatim. Also the extra skills to read (`strategium-ui` for UI squads; `source-driven-development` for external APIs/libraries; `debugging-and-error-recovery` when fixing failures; plus the theatre's **Extra skills** for that kind of squad), and "commit nothing".
- omp commits each isolated run on its task branch and cherry-picks it onto the run's branch when it ends. A result reporting a merge or stash conflict → one `task` agent resolves it on the run's branch.
- When a squad has landed, run one apothecary from eval. With `task.isolation.enabled` true (`omp config get task.isolation.enabled`), isolated and never applied, so its mutations never reach the branch: `agent("<brief>", agent="apothecary", isolated=True, apply=False)`. Otherwise (isolation is off) the Captain first commits the landed squad as a wip commit so `<base>..<head>` exists, then clones the run's branch into a fresh directory: `git clone -q --branch <branch> <repo> "$TEMP/<KEY>-apothecary-<n>"`, then `bun install --frozen-lockfile --cwd "$TEMP/<KEY>-apothecary-<n>"` (or the repo's install command run in that directory), and runs `agent("<brief>", agent="apothecary")` without `isolated`/`apply`. The apothecary deletes the clone at the end, after its restore proof. Skip it for a squad that is docs or prompts only, or that adds under about 30 lines of new production logic (comments, imports, types, logging and constants don't count): the inquisitor covers it, and the Captain says so in one line when the squad lands.
  - The brief has the squad's diff range `<base>..<head>`, the spec's acceptance criteria for that squad, the new or changed test files, the production paths, the baseline's known and flaky failures and the `## Checks` section of the auspex file (the fast tier's runner for each mutant, the full check tier's test command(s) to confirm survivors). When isolation is off, the brief (campaign and retrial) says `isolation is off`, gives the clone path as the only working directory, and gives the workspace path so the apothecary never touches it.
  - Effort is medium, also for a retrial after a veteran run.
  - A squad with `input: untrusted (<entry point>)` always gets the apothecary, even under the skip above; its brief carries the entry point, and says `fuzz only` when the skip applies.
  - With `NAMES on` the call gets `label="<name>"`, a name from `strategium name` for the agent `apothecary` (the retrial asks with `again: true`); an eval spawn whose label the plugin did not hand out is refused. With names off the label is free.
- Survivors, weak tests or fuzz crashes → a penance: a `battle-brother` fix run with the apothecary table (see Returns); a survivor's reproduction is a test that kills its mutant, and a fuzz crash enters the penance as an `F<n>` finding. After the penance, the apothecary retrial (medium like any other run) gets the previous survivors table (with the mutant diffs), the crash table (`F<n>` with exact inputs) if any, and the fix range, and re-checks only those survivors, those crash inputs and the lines the fix touched.
- A squad that fails twice (acceptance check red, or two fix runs that leave survivors) → one `veteran` run (same brief, plus the squad's lessons), which runs on the heavy tier. Still failing → stand down and show the user. The ladder: a squad's first builder runs on its planned tier, each later run of that squad one tier up, capped at heavy. Medium is the default for ordinary code because higher effort did not reliably pass more tests in published coding benchmarks; high is spent only on heavy squads and where medium visibly failed.
- Reuse: before a later round of a squad (a penance, or the veteran escalation), the Captain calls `strategium` `reuse <squad>` (it writes nothing). It answers `REUSE squad <target>: <id> (squad <src>, shared files, <n> tokens); <id> (squad <src>, same area, usage unknown)`, then `SEED brief line "Reuse: <best id>", the line "build squad <target>", the squad's lessons and open finding IDs, its commit(s) to git show, agent://<best id> (final report) and history://<best id>:-60; spawn the agent the ladder calls for (battle-brother for a penance, veteran for the escalation)` plus `; with names on, strategium action name with source: <best id>`. Candidates are agents of this run rated `proven` that have ended (never `corrupted`, `proven-regression`, unrated or running; with names off only an async builder, which reaches the cockpit registry, can be offered: a builder from a blocking task is not in it), whose squad shares files or a directory with the target squad (the target itself counts); shared files come before same area, then the fewest used tokens (a proxy: omp exposes no context fill to extensions), at most 3. With none: `REUSE squad <target>: none (no proven builder of this run that has ended shares its files or area); spawn a fresh builder`. With a candidate, the new spawn is still the agent the ladder calls for and counts as that round (same 2-round budget); its tier comes from the ladder, so a reuse never lowers it, and a corrupted round 1 followed by a reuse runs one tier up (the veteran heavy). The brief carries the line `Reuse: <best id>`, `build squad <target>`, the source's commit sha(s) (`git log --oneline origin/main..HEAD`) to read with `git show`, the instruction to read `agent://<id>` (its final report) and `history://<id>:-60` (its history tail) first, and the target squad's lessons and open finding IDs as for any penance. A `task` call whose brief or context names a `corrupted` agent in `Reuse:` is blocked, so spawn builders with `task`, not eval `agent()`. With names on, ask `name` with `source: <best id>`: the new builder takes the source's surname (`PenitentLorenzo`, `VeteranLorenzo`) and the squad's outcome stays with its first brother.
- A squad whose acceptance check cannot be satisfied as written is not a penance: redraft it (see Returns) instead of spending another round.
- `[seal] Commit` only when the run has the Commit seal (the commit setting at Muster, or the user's request).

### 5. Inquisition [inquisitor] → seal Demo
Hard rules: `rule://strategium-stations` (Inquisition).
- One `inquisitor` on `origin/main..HEAD` with `local://<KEY>-plan.md`. When the plan's first line under the Merge bar is `Review: confessor — <reason>` (the librarian or archmagos sets it), run one `confessor` in the same batch and add a `[confessor] Review` todo item. Add one `security-reviewer` in the same batch only if the diff touches auth, external input, secrets or network exposure.
- BLOCKING findings or FAIL items → a penance with all of them (by finding ID; a NOT REPRODUCED finding is dropped), then a retrial by the inquisitor on those IDs and the fix range. Max 2 rounds; then the item stays FAIL and the run shows the open items (see Returns). A new finding during a retrial opens no new round and goes to the user at Extraction.
- Ratings: after each reviewer report (and after each retrial), the Captain rates every agent of the run with `strategium` `rate` (`agent` = the id the task result shows, `rating`, `evidence`, `model`, `effort`; only the Captain calls it). The rating comes from the reviewers' reports and the checks, never from the agent's own report. Threshold: `corrupted` = a reproduced BLOCKING finding, an apothecary survivor or fuzz crash, a red acceptance check, or a rule breach (a commit, `git push`, a `gh` write, a write outside its worktree or scratch); a NOT REPRODUCED finding does not count. `proven-regression` = it passes but a new BLOCKING finding landed on the lines a penance touched. Otherwise `proven`. `evidence` is 1 to 8 short items (finding IDs, the failing check, the breached rule), each up to 200 characters; `rate` refuses an empty list. Rate at once, as `corrupted`, any agent that breaches a rule. `model` and `effort` are given by the Captain, not observed by the plugin: for a builder, its tier's selector split at the colon (`@task:medium` gives model `@task`, effort `medium`; the tier is the one the spawn note `Strategium tier <t>` named, selectors in `status` `TIERS`); for any other agent, the role's model (`@task`, `@smol`...) and its effort, or `default`. A squad that cannot pass as written is a redraft, not a corruption: do not rate its builder `corrupted` for that cause (it stays unrated unless other evidence corrupts it, so it is neither blamed nor reusable); `redraft` resets the ladder, so the re-planned squad starts at its planned tier with no step-up. A penance or veteran is a new agent and starts unrated. `corrupted` is permanent in the run: the agent can only be rated `corrupted` again (new evidence); any other rating is refused. Any other re-rate replaces the old one. With names on, a `corrupted` rating on a squad's latest builder (not retired by a redraft) counts as a fall at `end`, even if its job ended `completed`; the `FALL` line `rate` prints is provisional: the squad falls at end unless a later builder replaces it (a corrupted round-1 builder followed by a penance that is not corrupted stays a penance). A `redraft` keeps every rating (a retired builder's corruption no longer reaches the roster). A builder spawned by a blocking task is not in the cockpit registry, so its squad row shows no badge (the rating is still recorded). Ratings show in the cockpit (badge on the agent's and squad's row, `rating:`/`evidence:` lines in the detail) and in the debrief (`## Ratings`, per agent and per tier). For a `corrupted` rating the first item is `cause: <why it failed, at most 100 characters>` (the debrief's Evidence cell keeps the first 200 characters).
- Lessons: right after a `corrupted` rating the Captain writes the agent's lesson to `local://<KEY>-lessons.md` (`rate` ends its output with `LESSON write local://<KEY>-lessons.md for <id>`, plus `before the next round of squad <id>` for a builder; the plugin writes no file). One entry per corrupted agent: the heading `## <agent id> · squad <id> · <model> <effort>`, then the fields `Findings:` (IDs), `Reproduction:` (the test or command and its output, trimmed), `Tried:`, `Why it failed:` and `Do not:` (a short list), in that order. Every later round of that squad (a penance, the veteran run, or a reuse) quotes that squad's entries verbatim in its brief under `Lessons (do not repeat):`, and never the corrupted agent's raw report. For a `corrupted` rating the first `evidence` item is `cause: <why it failed, at most 100 characters>`, so the debrief keeps the cause that a later run can match (finding IDs mean nothing across runs); the lesson's `Why it failed:` agrees with it.
- Reconciliation when the confessor ran: a Merge bar item fails if either reviewer FAILs it. Hard rules: `rule://strategium-stations` (Extraction).

Their brief is the whole PR (`origin/main..HEAD`) against the Merge bar, with no earlier reports. This is the confessor's second allowed use, besides the plan's `Review: confessor` line. BLOCKING findings from either, or NON-BLOCKING ones the user picks in one `ask`, go to a penance with every finding ID; each reviewer then re-checks only its own IDs on the fix range. Fix commits: after the penance lands, `git reset --soft <pushed head sha>` and commit the fix as new Conventional Commits on top of the pushed ones (the Commit seal, if the run has it, asks first), pushed with a plain `git push` without a new MR seal; the pipeline on the final head must be green before `gh pr merge`. The loop has its own 2-round budget, separate from Inquisition's, and no `veteran` run; NOT REPRODUCED findings are dropped and a new NON-BLOCKING finding in a retrial opens no new round and is shown to the user. Only a retrial where every ID is FIXED and no new BLOCKING finding appeared reaches clean (and no picked NON-BLOCKING is open) → the theatre's ready, Status, comment and merge steps.
